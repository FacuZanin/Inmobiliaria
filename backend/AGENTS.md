PRINCIPIO GENERAL El agente NO debe entender el sistema completo. Debe: resolver tareas puntuales con el mínimo contexto posible evitando exploración del repositorio REGLAS CRÍTICAS (OBLIGATORIAS) Prohibido explorar el proyecto No hacer: búsqueda global del repo lectura de módulos no mencionados inspección de carpetas completas análisis de arquitectura completa sin pedido explícito Prohibido cargar múltiples archivos innecesarios Solo se pueden abrir: archivos mencionados explícitamente por el usuario archivos directamente relacionados al error o feature Máximo recomendado: 1 a 3 archivos por tarea Prohibido leer logs completos Si hay errores: usar SOLO el stack trace relevante máximo 30–50 líneas ignorar logs de build completos ESTRATEGIA DE CONTEXTO (OBLIGATORIA) Nivel 1 — Diagnóstico Solo: error archivo afectado función específica Nivel 2 — Corrección Solo: archivo actual dependencias directas Nivel 3 — Refactor (si se solicita) Solo: módulo específico sin expandir a otros módulos REGLA DE SCOPE Cada tarea debe limitarse a: 1 módulo / 1 feature / 1 bug Nunca mezclar: auth + propiedades + uploads audit + permisos + publicaciones REGLA DE MINIMIZACIÓN DE TOKENS Antes de leer un archivo, el agente debe preguntarse: “¿Este archivo es estrictamente necesario para resolver esto?” Si la respuesta no es 100% sí → NO leerlo. ESTRUCTURA IDEAL DE TRABAJO Entrada ideal del usuario: error concreto archivo concreto función concreta Ejemplo: Error en login en auth.service.ts al validar token Entrada NO ideal: Revisá todo el sistema de autenticación COMPORTAMIENTO DEL AGENTE El agente debe: asumir contexto mínimo no reconstruir arquitectura completa no proponer refactors globales sin pedido evitar explicaciones largas priorizar patches pequeños OUTPUT (MUY IMPORTANTE) Respuestas deben ser: código primero explicación mínima o nula sin redundancia sin reexplicar arquitectura OPTIMIZACIÓN AVANZADA (MODO PRO) Si el proyecto es grande: trabajar por “micro-tareas” dividir bugs en pasos evitar análisis transversal del sistema
